# spec-retire

`docs/specs/<name>.md`는 **구현용 임시 문서**다. 구현이 끝나면 그 내용은 두 곳으로 간다.

- **동작** → `tests/` (틀리면 코드가 깨졌다고 말할 수 있는 것)
- **근거** → `docs/adr/` (다시 결정하려면 필요한 것)

둘 다 아닌 것은 유실시킨다. 이관이 끝나면 spec 파일을 **삭제**한다.

## 절대 규칙

- **작업자에게 질문하지 않는다.** 확인·승인·선택을 요청하지 않는다. 단일 턴에 끝낸다.
- **판단이 서지 않으면 테스트로 보낸다.** 기본값은 보존이다.
- 아래 `유실 화이트리스트`에 없는 내용은 유실시키지 않는다.

## 0단계 — 선행 조건

하나라도 불충족이면 **아무것도 하지 않고 한 줄 보고 후 종료한다.** 이 스킬은 조기 발동되어도 무해해야 한다.

1. 테스트 환경이 있다 — `CLAUDE.md`에 `## Testing` 섹션이 있고 테스트 명령이 동작한다
   - 없으면: `테스트 환경이 없어 spec 정리를 건너뜁니다. /tdd-setup을 먼저 실행하세요.`
2. 대상 spec이 있다 — 인자로 받은 spec, 없으면 이번 세션에서 구현한 spec
   - 없으면: `정리할 spec이 없습니다.`
3. 대상 spec의 기능이 실제로 구현되어 있다 — 해당 기능의 `app/api/*/route.ts`나 페이지가 존재한다
   - 없으면: `아직 구현되지 않은 spec입니다. 구현 후 다시 실행하세요.`

## 1단계 — 읽기

다음을 읽는다. 범위를 넘겨 코드베이스 전체를 훑지 않는다.

- 대상 `docs/specs/<name>.md`
- `docs/domain-story.md` (있으면) — 용어를 여기에 맞춘다
- `docs/PRD.md` (있으면) — `Out of Scope`와 `Further Notes`만
- **이 feature의 구현 코드**: `app/api/<feature 관련>/route.ts`, `types/index.ts`, `schema.sql`
  - route 파일을 읽는 것은 필수다. 테스트 규칙(`.claude/rules/testing.md`)이 이 시점에 로드된다
- `docs/adr/` 기존 목록 (번호와 제목만)
- `tests/` 기존 테스트 목록

## 2단계 — 문장 추출과 라벨링

spec의 모든 문장을 아래 기준으로 **빠짐없이** 라벨링한다.

> **이 문장이 틀렸을 때, 코드가 깨졌다고 말할 수 있는가?**
>
> - **Yes** → `TEST`
> - **No, 그런데 다시 결정하려면 필요하다** → `ADR`
> - **둘 다 아니다** → `DISCARD` (아래 화이트리스트에 해당할 때만)

### 유실 화이트리스트

`DISCARD`는 다음 다섯만 허용한다. 여기 없으면 `TEST` 또는 `ADR`로 보낸다.

1. LLM 출력의 **내용 품질**에 대한 기대 (예: "이 관점이 이상 징후를 잡는다")
2. User Story의 `so that` 절 (benefit)
3. **다른 파일이 원본**인 사실
   - 스키마 → `schema.sql` / 아키텍처 제약 → `CLAUDE.md` / 프롬프트 문구 → 프롬프트 파일
4. 완료 후 무의미해진 계획 (빌드 순서, 우선순위, core/nice-to-have 구분)
5. **화면 표시·화면 간 이동** 등 Presentation 레이어 동작
   - seam이 route 핸들러라 검증할 수 없다. 비개발자 도구에 UI 회귀 테스트를 요구하지 않기로 한
     **의식적 선택**이며, 이 문장들 때문에 seam을 넓히지 않는다.
   - 예: "행을 클릭하면 상세로 이동한다", "등급을 Badge 색으로 구분한다", "필터가 URL에 유지된다"

> ⚠️ 5번의 경계 — **화면이 그리는 데이터는 유실이 아니다.**
> "무엇이 내려오는가"는 `TEST`, "그것을 화면에 어떻게 그리는가"만 `DISCARD`다.
> 예) "목록이 최신순으로 보인다" → 정렬은 route 응답으로 `TEST`, 표로 렌더한다는 사실만 유실.
> 화면이라는 단어가 들어갔다는 이유로 서버 동작까지 5번으로 밀지 않는다.

### 섹션별 기본 처리

| spec 섹션 | 기본 |
|---|---|
| Problem Statement / Solution | `DISCARD` (3번 — domain-story가 원본) |
| User Stories | 서버 동작이면 `TEST` / 화면 동작은 `DISCARD`(5번) / `so that` 절은 `DISCARD`(2번) |
| Implementation Decisions | 계약·규칙·상태 전이는 `TEST` / 구조 선택은 `ADR` |
| Out of Scope | `ADR` |
| Further Notes | 합의된 트레이드오프는 `ADR`, 나머지는 `DISCARD` |

각 `TEST` 문장에 대해 **이미 통과하는 테스트가 있는지** 확인한다. 있으면 `COVERED`로 표시하고 넘어간다.

## 3단계 — 테스트 보강

`TEST`이면서 `COVERED`가 아닌 문장마다 테스트를 작성한다.

### seam

`.claude/rules/testing.md` 또는 `CLAUDE.md`에 정의된 seam을 따른다. **작업자에게 묻지 않는다.**
정의가 없으면 기본값을 쓴다.

- 기본: `app/api/*/route.ts` 핸들러를 직접 호출한다 (HTTP 서버를 띄우지 않는다)
- 예외: `lib/`의 입출력 없는 순수 함수
- 금지: 페이지 컴포넌트 렌더 테스트, 브라우저 e2e, `lib/db.ts` 내부

### 규칙

- **기대값은 spec 문장에서 가져온다. 코드를 실행한 결과를 보고 채우지 않는다.**
  spec에 리터럴로 적힌 매핑·이벤트명·조건을 그대로 쓴다.
- `claude -p` 등 외부 프로세스 호출은 **고정 응답으로 대체**한다. 검증 대상은 "LLM이 무엇을
  답하는가"가 아니라 "그렇게 답했을 때 시스템이 어떻게 처리하는가"다.
- DB는 모킹하지 않는다. 임시 SQLite 파일을 쓰고 테스트마다 격리한다.
  - `getDB()`가 `process.cwd()` 기준으로 DB 파일을 잡는 구조라면, 테스트마다 임시 디렉터리를
    만들고 `schema.sql`을 복사한 뒤 `process.chdir()` 한다. 싱글톤이 캐시되므로
    `vi.resetModules()` 후 대상 모듈을 **동적 import** 해야 새 DB가 잡힌다.
  - ⚠️ `vi.resetModules()`는 mock 모듈도 다시 평가한다. 외부 프로세스 stub의 상태를 모듈
    최상위 `const`로 두면 **테스트가 보는 객체와 mock이 쓰는 객체가 갈라진다.**
    stub 상태는 `globalThis`에 고정한다. (실측에서 이 함정으로 테스트 6건이 한 번에 실패했다)
- 파일은 spec 하나당 하나다: `tests/<spec-name>.test.ts`
- test name에 출처를 표기한다: `US-9: 어느 관점이든 high면 종합이 high가 된다`

### 금지 패턴 — 작성 후 스스로 점검한다

테스트를 실행하기 전에 자기가 쓴 테스트를 훑어 다음이 있으면 고친다.

- 단언이 없다
- 응답 `status`만 확인하고 내용을 보지 않는다
- `try`/`catch`로 감싸 에러를 삼킨다
- 기대값이 실행 결과에서 복사된 것으로 보인다

## 4단계 — ADR 작성

### ADR-0001 — 구현 범위 (커버리지 맵)

`docs/adr/0001-구현범위.md`가 **없으면 만든다.** 있으면 범위가 늘어난 만큼 **행을 추가**한다
(범위 확장은 결정 번복이 아니므로 append-only를 깨지 않는다).

domain-story의 업무 단계를 세로축에 놓고, 각 단계를 시스템이 어디까지 덮는지 적는다.

`docs/domain-story.md`가 없으면(`scaffold`만 거친 프로젝트) PRD의 `Problem Statement`에 적힌
현행 업무 흐름에서 단계를 뽑는다. 그래도 못 뽑으면 화면·API가 아니라 **심사·접수·통보처럼
사람이 하는 일의 단위**로 적는다. 기능 목록을 세로축에 놓으면 커버리지 맵이 아니라 기능 목록이 된다.

```markdown
# ADR-0001 — 구현 범위

<PRD의 Problem/Solution을 2~3문장으로>

## 커버리지

| 업무 단계 | 커버 | 남는 사람 몫 |
|---|---|---|
| ... | 시스템 / 부분 / 없음 | ... |

## 해석에 영향을 주는 제외

- **<항목>** — <무엇이 달라지는가>

## 검증되지 않는 것

- **화면 표시·화면 간 이동** — 테스트 seam이 API route라 자동 검증되지 않는다.
  서버가 무엇을 내려주는지는 테스트가 잠그지만, 그것을 화면에 어떻게 그리는지는 사람이 열어 확인한다.
```

`검증되지 않는 것` 절은 **항상 위 문구 그대로 넣는다.** 유실 화이트리스트 5번으로 버려진 문장이
어디로 갔는지 남기는 자리이며, "화면 동작은 검증 안 된다"가 사고가 아니라 선택임을 고정한다.

`Out of Scope` 항목은 다음 기준으로 가른다.

> **이 제외가 사용자의 결과 해석을 바꾸는가?**
>
> - **바꾼다** → ADR-0001의 `해석에 영향을 주는 제외`
> - **안 바꾼다** → 관련 기술 ADR의 `버린 대안`으로 흡수

### ADR-0002 이후 — 기술 결정

`Implementation Decisions` 중 **대안이 존재했던 항목만** ADR로 만든다.

> **다르게 할 수 있었는가? 다르게 했다면 무엇이 달라졌는가?**
> 둘 다 답할 수 있어야 ADR이다. 못 하면 그것은 결정이 아니라 구현 사실이므로 `TEST`나 `DISCARD`다.

기존 `docs/adr/`에 **같은 결정이 이미 있으면 새로 만들지 않는다.**

```markdown
# ADR-NNNN — <결정을 한 문장으로, 현재형>

## 맥락
<왜 이 결정이 필요했는가. domain-story의 용어를 쓴다>

## 버린 대안
- **<대안>** — <버린 이유>

## 결과
<이 결정 때문에 사용자가 감수하는 것>

## 동작
`tests/<file>.test.ts` 참조
```

### ADR 금지 사항

- **`버린 대안`을 채울 수 없으면 ADR을 만들지 않는다.**
- 동작 상세·코드·파일 경로·수치 규칙 본문을 다시 쓰지 않는다. 테스트 파일 참조로만 가리킨다.
  (이를 어기면 ADR이 코드와 동기화해야 하는 문서가 되어 목적이 무너진다)
- 기존 ADR을 수정하지 않는다. 결정이 뒤집히면 새 ADR을 추가하고 옛 문서에
  `superseded by: NNNN` 한 줄만 덧붙인다.

## 5단계 — 검증

1. 전체 테스트를 실행한다.
2. **실패가 있으면 spec을 삭제하지 않는다.** 사후 테스트가 실패했다는 것은 spec에 적힌 내용 중
   **실제로 구현되지 않은 것**이 있다는 뜻이다. 실패 항목을 보고하고 종료한다.
3. 미라벨 문장이 하나라도 남아 있으면 삭제하지 않는다. 라벨링을 마저 한다.

## 6단계 — 제거와 커밋

1. 대상 `docs/specs/<name>.md`를 **삭제**한다. archive로 옮기지 않는다 — git 히스토리가 원본이다.
2. `docs/specs/`가 비면 디렉터리도 지운다.
3. `docs/PRD.md`는 모든 spec이 정리된 뒤에만 삭제한다.
4. `commit` 스킬로 커밋한다. 커밋 본문에 라벨링 결과를 남긴다.

```
docs: <feature> spec을 테스트와 ADR로 이관

- 테스트 n건 (신규 n / 기존 n)
- ADR n건: NNNN-..., NNNN-...
- 유실 n건 (화면 동작 n건): <항목명 나열>
```

유실 항목명을 반드시 적는다. 화면 동작(5번)은 건수를 따로 적어 검증 공백의 크기가 보이게 한다. 나중에 `git show`로 spec 원본과 대조해 되살릴 수 있어야 한다.

## 보고

작업자에게 한국어로 짧게 보고한다. 파일 목록과 건수만 적고 과정을 서술하지 않는다.
