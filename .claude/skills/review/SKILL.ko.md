현재 세션에서 구현한 작업을 두 축으로 리뷰합니다:

- **표준(Standards)** — 코드가 이 저장소에 문서화된 코딩 표준을 따르는가?
- **스펙(Spec)** — 코드가 그 기반이 된 스펙을 충실히 구현했는가?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브 에이전트**로 실행되며, 이 스킬이 그 결과를 종합합니다.

## 과정

### 1. 리뷰 대상 파악

리뷰 대상은 현재 작업을 구현하면서 만들거나 수정한 파일들입니다 — 지금까지의 세션(논의된 내용, 구현한 스펙, 작성한 코드)을 통해 이미 알고 있을 것입니다. 구체적인 경로로 명시적으로 나열하세요.

그런 맥락이 없다면(예: 스킬이 새 세션에서 바로 호출된 경우), 사용자에게 어떤 파일이나 영역을 리뷰할지 물어보세요.

더 진행하기 전에, 파일 목록이 비어있지 않고 모든 경로가 실제로 존재하는지 확인하세요. 대상이 비어있거나 파일이 없으면 여기서 실패해야 합니다 — 두 개의 병렬 서브 에이전트 안에서가 아니라.

### 2. 스펙 출처 파악

작업의 기반이 된 스펙을 다음 순서로 찾으세요:

1. 사용자가 인자로 전달한 경로.
2. `docs/specs/` 아래의 일치하는 스펙 (예: 방금 구현한 기능이라면 `docs/specs/<name>.md`).
3. 아무것도 찾지 못하면 사용자에게 스펙이 어디 있는지 물어보세요. 스펙이 없다고 하면 **Spec** 서브 에이전트는 건너뛰고 "사용 가능한 스펙 없음"이라고 보고합니다.

### 3. 표준 출처 파악

`CODING_STANDARDS.md`나 `CONTRIBUTING.md`처럼, 저장소 안에서 코드를 어떻게 작성해야 하는지 문서화한 것이라면 무엇이든 해당합니다.

저장소가 문서화한 것에 더해, Standards 축은 항상 아래의 **스멜 기준선(smell baseline)** — 저장소가 아무것도 문서화하지 않아도 적용되는, 고정된 Fowler 코드 스멜 목록(_Refactoring_, 3장) — 을 함께 지닙니다. 여기에는 두 가지 규칙이 적용됩니다:

- **저장소가 우선한다.** 문서화된 저장소 표준은 항상 이깁니다; 기준선이 지적할 만한 것을 저장소가 오히려 권장한다면, 그 스멜 지적은 무시하세요.
- **항상 판단의 영역이다.** 각 스멜은 하드한 위반이 아니라 이름 붙은 휴리스틱("Feature Envy 가능성 있음")일 뿐입니다 — 그리고 여기 있는 다른 모든 표준과 마찬가지로, 이미 툴링이 강제하는 것은 건너뛰세요.

각 스멜은 *무엇인지* → *어떻게 고치는지* 순으로 읽습니다; 구현된 코드에 대입해 보세요:

- **Mysterious Name(모호한 이름)** — 함수, 변수, 타입의 이름이 그것이 무엇을 하는지/담고 있는지 드러내지 않음. → 이름을 바꿔라; 정직한 이름이 떠오르지 않는다면 설계 자체가 불명확한 것이다.
- **Duplicated Code(중복 코드)** — 같은 로직 형태가 변경 사항 안에 두 곳 이상 나타남. → 공통 형태를 추출해서 양쪽에서 호출하라.
- **Feature Envy(기능 욕심)** — 어떤 메서드가 자신의 데이터보다 다른 객체의 데이터를 더 많이 들여다봄. → 그 메서드를 욕심내는 데이터가 있는 쪽으로 옮겨라.
- **Data Clumps(데이터 뭉치)** — 같은 몇 개의 필드나 매개변수가 계속 함께 몰려다님(하나의 타입으로 태어나고 싶어함). → 하나의 타입으로 묶어서 그것을 전달하라.
- **Primitive Obsession(원시 타입 집착)** — 자신만의 타입을 가질 자격이 있는 도메인 개념을 원시값이나 문자열이 대신하고 있음. → 그 개념에 작은 전용 타입을 부여하라.
- **Repeated Switches(반복되는 분기)** — 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 사항 전체에 반복해서 나타남. → 다형성으로 대체하거나, 양쪽이 공유하는 맵 하나로 바꿔라.
- **Shotgun Surgery(산탄총 수술)** — 논리적으로 하나인 변경이 여러 파일에 흩어진 수정을 강제함. → 함께 바뀌는 것들을 하나의 모듈로 모아라.
- **Divergent Change(엇갈린 변경)** — 하나의 파일이나 모듈이 서로 관련 없는 여러 이유로 수정됨. → 각 모듈이 하나의 이유로만 바뀌도록 분리하라.
- **Speculative Generality(투기성 일반화)** — 스펙에 없는 필요를 위해 추가된 추상화, 매개변수, 훅. → 삭제하라; 실제 필요가 나타날 때까지 다시 인라인화하라.
- **Message Chains(메시지 체인)** — 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 형태의 탐색. → 그 탐색 경로를 첫 번째 객체의 메서드 하나 뒤로 숨겨라.
- **Middle Man(중간 관리자)** — 대부분 그냥 다음으로 위임만 하는 클래스나 함수. → 잘라내고 실제 대상을 직접 호출하라.
- **Refused Bequest(거부된 상속)** — 상속받은 것 대부분을 무시하거나 오버라이드하는 서브클래스나 구현체. → 상속을 버리고 컴포지션을 사용하라.

### 4. 두 서브 에이전트를 병렬로 생성

`Agent` 도구 호출 두 개를 하나의 메시지에 담아 보내세요. 둘 다 `general-purpose` 서브 에이전트를 사용하세요.

**Standards 서브 에이전트 프롬프트** — 다음을 포함하세요:

- 리뷰할 구현 파일 목록과, 그것들을 읽으라는 지시.
- 3단계에서 찾은 표준 출처 파일 목록, **그리고 3단계의 스멜 기준선 전문**을 그대로 붙여넣기 — 서브 에이전트는 그것에 접근할 다른 방법이 없습니다.
- 지시문: "나열된 파일들을 읽어라. 관련 있는 곳마다 파일 단위로 — (a) 문서화된 표준을 코드가 위반하는 모든 지점을 보고하라: 표준을 인용하라(파일 + 규칙); 그리고 (b) 발견한 모든 기준선 스멜: 이름을 대고 코드를 인용하라. 하드한 위반과 판단이 필요한 사항을 구분하라 — 문서화된 표준 위반은 하드할 수 있지만, 기준선 스멜은 항상 판단의 영역이며, 문서화된 저장소 표준이 기준선보다 우선한다. 툴링이 강제하는 것은 건너뛰어라. 400단어 이내로."

**Spec 서브 에이전트 프롬프트** — 다음을 포함하세요:

- 리뷰할 구현 파일 목록과, 그것들을 읽으라는 지시.
- 스펙의 경로나 내용.
- 지시문: "스펙과 나열된 파일들을 읽어라. 보고하라: (a) 스펙이 요구했지만 빠졌거나 일부만 구현된 요구사항; (b) 요청받지 않았는데 코드에 있는 동작(스코프 크리프); (c) 구현된 것처럼 보이지만 구현이 잘못된 것 같은 요구사항. 각 발견 사항마다 스펙의 해당 줄을 인용하라. 400단어 이내로."

스펙이 없으면 Spec 서브 에이전트를 건너뛰고 최종 보고서에 이를 명시하세요.

### 5. 종합

두 보고서를 `## Standards`와 `## Spec` 제목 아래, 그대로 또는 가볍게 정리해서 제시하세요. 두 축을 병합하거나 재정렬하지 **마세요** — 이 둘은 의도적으로 분리돼 있습니다(아래 "왜 두 축인가" 참고).

한 줄 요약으로 마무리하세요: 축별 총 발견 건수, 그리고 (있다면) *각 축 안에서* 가장 심각한 문제. 축을 가로질러 단일 승자를 뽑지 마세요 — 그것은 이 분리가 막으려는 재정렬 그 자체입니다.

## 왜 두 축인가

변경 사항은 한 축은 통과하고 다른 축은 실패할 수 있습니다:

- 모든 표준을 따르지만 잘못된 것을 구현한 코드 → **Standards 통과, Spec 실패.**
- 스펙이 요구한 그대로지만 프로젝트의 관례를 깨는 코드 → **Spec 통과, Standards 실패.**

둘을 따로 보고하면 한 축이 다른 축을 가리는 것을 막을 수 있습니다.
