# ADR-0004 — 장애등급 판정 이력과 과거 장애 이력은 별개 테이블로 분리하고, 둘 다 조회 전용으로 둔다

## 맥락

`incident_records`(장애등급-계산 도구가 자동 산정한 결과 스냅샷)와 `incident_logs`(엑셀로 수기 관리해온 실제 과거 장애 대장)는 출처와 목적이 다르다. 전자는 도구가 만들고, 후자는 사람이 기록해온 원본을 그대로 옮긴 것이다. 두 화면 모두 "지금까지의 이력을 찾아본다"는 요구만 있고, 등록/수정/삭제·통계·내보내기까지 범위를 넓히면 각 이력의 원본성을 보존한다는 목적과 충돌한다.

## 버린 대안

- **두 이력을 하나의 테이블/화면으로 통합하는 것** — 스냅샷 데이터와 수기 기록이 섞여 어느 값이 도구 산정 결과이고 어느 값이 사람이 적은 원본인지 구분하기 어려워진다.
- **두 화면에 등록·수정·삭제(CRUD), 통계·차트, 엑셀 내보내기 기능을 포함하는 것** — 이번 범위(목록·상세 조회)를 넘어선다.
- **`incident_logs`의 관계사(자유 텍스트)를 `companies` 테이블과 매핑·연동하는 것** — 원본 엑셀의 관계사 표기가 `companies` 데이터와 정확히 일치한다는 보장이 없다.
- **팀명·관계사 필터용 distinct-value 조회 API를 별도로 만드는 것** — 목록 API가 이미 반환하는 데이터에서 뽑아 쓰는 것으로 충분하다.
- **년도/분기/년월을 별도 컬럼으로 저장하는 것** — 발생일(occurred_date)로 파생 가능하고, 원본 엑셀에는 발생일과 년월이 서로 맞지 않는 오기도 있었다.

## 결과

`incident_records`와 `incident_logs`는 완전히 독립된 테이블이며, 둘 다 조회(목록·상세) API만 제공한다(POST/PATCH/DELETE 없음). 관계사 표기가 계열사마다 다르면 필터·집계에서 서로 다른 값으로 취급된다. 통계, 내보내기, 이력 정정이 필요하면 이번 범위 밖의 별도 작업이 필요하다.
